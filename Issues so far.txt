Overall shape:
A hub-and-spoke network in eu-central-1. There are 2 VPCs, one holds web server, DB and Monitoring in separate subnets and has no direct access to the internet. The webservers have 2 subnets in different AZ. The other VPC is reserved for the DMZ where there are the Load Balancer and the NAT gateway, this VPC is connected to the Internet and uses a Transit Gateway in between the two VPC for communication. To note the Transit Gateway also has its own subnet in the DMZ, because when routing a subnet it can only have one route per destination. The Transit Gateway attachment's ENI needed a completely different rule for its outbound traffic ( traffic going anywhere on the internet -> send to NAT gateway) Why not NAT and IGW directly? Because the traffic passing through that ENI originates from the internal VPC and the IPs aren't routable on the public internet so they need NAT to translate them to its public IP before going out.

How traffic actually gets to the internet:
Instance in the internal VPC needs internet access sends its outbound traffic to the TGW following the pstatic default route I added, then it forwards it to the DMZ VPC attachment of the TGW in its subnet, where It routs to the NAT Gateway where it finally sens it thought the IGW with public IP and return traffic follow the same path in reverse.

Database:
The database tier is a single EC2 instance in the internal VPC running MySQL 8 community, bootstrapped via user_data on the first boot. That script had a little bug where MySQL community repo ships a 2022 GPG signing key, but the actual packages are now using the 2023 key, so it was silently failing. The EC2 itself was launching fine, but the software never actually installed. I fixed it by importing the 2023 key before the install. But user_data only executes once and any editing is not applied so I needed to force it to re-execute and replace the aws instance db.

The web tier and the target group problem
The web tier is an Auto Scaling Group begind an Application Load Balancer with instances launch template. The problem was that ALB lives inside the DMZ VPC and the instances live in the internal VPC so the default configuration wouldn't work as it required an IP for across VPCs. And since it required a specific IP address that meant that I would need to use another mechanism to register and deregister instances as ASG scales. And that's how it came to using Lambda, since as it turns out it is the exact reason Lambda exists for. So what I have now is 2 lifecycle hooks that are launching and terminating. Simply explained what happens is that hooks pause instances mid transition and is told to pause until told otherwise. During that time events are emmited and are caught by EventBridge via a rule, which triggers a Lambda function. The Lambda looks up the instance IP and calls RegisterTargets or DeregisterTargets against the ALB's target group directly thought the ELB API and then lets the instance finish its process. One bug I hit here was that RegisterTargets requires an explicit AvailabilityZone: 'all' field on the target when the IP address lives outside the target group's own VPC, without it AWS returns a validation error. This combined with the launch hook's Abandon result was creating a loop where instances would launch, fail to register and get abandoned, terminated and the ASG would then launch a replacement and do that on repeat. Since the two thigns I described needed to be lined up for this to happen I just decided to add the AvailabilityZone: 'all' field and it was pretty much fixed.
